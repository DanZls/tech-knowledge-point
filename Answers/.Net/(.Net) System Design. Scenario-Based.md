## Implement Role-Based Authorization (claims, [Authorize(Roles=...)], policy-based authorization)
In ASP.NET Core, role-based authorization checks whether the authenticated user's claims contain a specific role before allowing access to an endpoint. Roles are typically embedded as claims (`ClaimTypes.Role`) inside the JWT or cookie identity during sign-in, and the middleware reads them from `HttpContext.User`. The simplest approach is decorating a controller or action with `[Authorize(Roles = "Admin,Manager")]`, which allows access if the user has any of the listed roles. For more granular rules — e.g., combining roles with department or claim values — policy-based authorization is preferred: you register named policies in `AddAuthorization` using `RequireRole`, `RequireClaim`, or a custom `IAuthorizationRequirement`/`AuthorizationHandler`. Policies centralize authorization logic, avoid scattering role strings across the codebase, and support complex conditions like "Manager AND same department as resource". On Azure, roles can come from Entra ID (Azure AD) App Roles or groups, mapped into claims automatically by the OpenID Connect middleware. Always fail closed (deny by default) and apply `[Authorize]` globally with `[AllowAnonymous]` only where needed, rather than relying on inconsistent per-action attributes. For resource-level checks (e.g., a manager modifying only their own team's data), combine role checks with resource-based authorization handlers that inspect the resource owner against the current user's claims.

```csharp
// Simple role check
[Authorize(Roles = "Admin")]
[HttpDelete("{id}")]
public IActionResult DeleteUser(int id) => Ok();

// Policy-based authorization
builder.Services.AddAuthorization(options => {
    options.AddPolicy("CanManageTeam", policy =>
        policy.RequireRole("Manager")
              .RequireClaim("Department", "Engineering"));
});

[Authorize(Policy = "CanManageTeam")]
[HttpPost("approve")]
public IActionResult Approve() => Ok();
```

## Design a secure JWT Login API (password hashing, short expiration, refresh tokens, RS256 signing)
A secure JWT login endpoint starts by never storing plaintext passwords: use `ASP.NET Core Identity`'s `PasswordHasher<T>` (PBKDF2 with a per-user salt) or a modern algorithm like Argon2/BCrypt, and compare hashes in constant time. On successful login, issue a short-lived access token (5–15 minutes) signed with an asymmetric algorithm (RS256) so the private key stays only on the auth server while resource servers verify with the public key — this avoids sharing a symmetric secret across services. Alongside the access token, issue a long-lived, opaque refresh token stored server-side (hashed, in SQL) with an expiration and rotation policy; when refreshed, the old token is invalidated to detect reuse/theft. Access tokens should carry minimal claims (sub, roles, exp, iss, aud) — never sensitive data — and be transmitted over HTTPS only, ideally stored in memory or an `HttpOnly, Secure, SameSite=Strict` cookie rather than `localStorage` to reduce XSS token theft risk. Rate-limit the login endpoint to prevent brute-force and credential-stuffing attacks, and lock accounts temporarily after repeated failures. On Azure, RS256 keys can be managed and rotated via Azure Key Vault, and Entra ID can replace a custom auth server entirely for enterprise scenarios. Always validate `iss`, `aud`, `exp`, and signature on every request, and use a key rotation strategy (`kid` header) so old tokens gracefully expire without a hard cutover.

```csharp
// Hash password on register
var hasher = new PasswordHasher<User>();
user.PasswordHash = hasher.HashPassword(user, plainPassword);

// Verify on login
var result = hasher.VerifyHashedPassword(user, user.PasswordHash, plainPassword);
if (result == PasswordVerificationResult.Failed) return Unauthorized();

// Issue RS256-signed access token
var credentials = new SigningCredentials(rsaSecurityKey, SecurityAlgorithms.RsaSha256);
var token = new JwtSecurityToken(
    issuer: "auth.myapp.com",
    audience: "myapp.api",
    claims: new[] { new Claim(ClaimTypes.NameIdentifier, user.Id.ToString()) },
    expires: DateTime.UtcNow.AddMinutes(10),
    signingCredentials: credentials);
```

## Frontend-backend sync failure due to a missing foreign key on save — how do you validate safely?
This scenario happens when the frontend sends a payload referencing a related entity (e.g., `DepartmentId`) that no longer exists or was never created, causing a foreign key constraint violation at the database level. Relying solely on the database constraint is unsafe because it surfaces as a generic 500 error and leaves the user without actionable feedback. The correct fix is defensive validation at the application boundary: before calling `SaveChanges`, explicitly check that referenced IDs exist (e.g., `await _context.Departments.AnyAsync(d => d.Id == dto.DepartmentId)`), returning a clear `400 Bad Request` with a validation message if not. For high-throughput scenarios, batch these existence checks or use a single query with `Contains` for multiple foreign keys instead of one query per key. Additionally, wrap the actual `SaveChanges` call in a try/catch for `DbUpdateException`, inspecting the inner `SqlException` for constraint violation codes (547) as a safety net for race conditions between the check and the save. On the frontend, ensure dropdowns/selectors are populated from the same source of truth and refreshed if stale, and disable submission until required references are confirmed to exist. Logging the failed payload (without sensitive data) helps diagnose whether it's a stale cache, a race condition, or a genuine data integrity bug. Idempotent, well-documented error responses (RFC 7807 Problem Details) let the frontend map errors to specific fields.

```csharp
public async Task<IActionResult> SaveOrder(OrderDto dto) {
    var departmentExists = await _context.Departments
        .AnyAsync(d => d.Id == dto.DepartmentId);

    if (!departmentExists)
        return BadRequest(new { field = "DepartmentId", error = "Department not found" });

    try {
        _context.Orders.Add(dto.ToEntity());
        await _context.SaveChangesAsync();
    } catch (DbUpdateException ex) when (ex.InnerException is SqlException { Number: 547 }) {
        return Conflict("Related record no longer exists");
    }

    return Ok();
}
```

## Pushing schema changes (new nullable columns) safely without breaking production
Safe production schema changes rely on backward-compatible, additive migrations combined with a decoupled deployment sequence. Adding a new column should always be nullable (or have a `DEFAULT` value) so existing INSERT/UPDATE statements from the currently running application version keep working without modification — never add a `NOT NULL` column without a default in one step. The recommended sequence is: (1) deploy the migration that adds the nullable column while the old application code is still running, (2) deploy the new application code that starts reading/writing the column, and (3) only in a later migration, if required, backfill data and tighten the constraint to `NOT NULL`. This "expand and contract" pattern avoids downtime because at no point does a currently running app version encounter a schema it doesn't understand. On SQL Server, adding a nullable column is a fast metadata-only operation, but adding a column with a non-null default on a large table can trigger a size-of-data operation pre-2016 SP2, so always test on a production-sized copy or use `ONLINE = ON` where supported. Use EF Core migrations checked into source control, reviewed like any other code change, and run automatically via CI/CD (Azure DevOps/GitHub Actions release pipeline) rather than manually against production. Feature flags can further decouple "schema is ready" from "feature is visible", letting you roll changes forward or back without additional migrations.

```csharp
// Migration: additive-only change
public partial class AddMiddleNameToUser : Migration {
    protected override void Up(MigrationBuilder migrationBuilder) {
        migrationBuilder.AddColumn<string>(
            name: "MiddleName",
            table: "Users",
            type: "nvarchar(100)",
            nullable: true); // safe: no default required, no existing rows break
    }
}
```

## Handling brief network drops when consuming a third-party microservice (retry policies, e.g., Polly)
Transient failures like brief network drops, timeouts, or 502/503 responses from a downstream microservice should be handled with a retry policy rather than immediately surfacing an error to the user. Polly, the standard .NET resilience library, provides a `RetryPolicy` that can retry a failed HTTP call a configured number of times with exponential backoff and jitter, avoiding a "thundering herd" where all clients retry simultaneously and overwhelm a recovering service. Retries should only apply to idempotent operations (GET, PUT with idempotency keys) or truly transient errors — retrying a non-idempotent POST blindly can create duplicate side effects, so pair retries with idempotency keys where writes are involved. Combine retry with a Circuit Breaker policy so that after a threshold of consecutive failures, the circuit "opens" and fails fast for a cooldown period instead of hammering an already-struggling service, then moves to "half-open" to test recovery. Polly integrates directly with `HttpClientFactory` via `AddPolicyHandler`, so policies apply transparently to all calls through a named/typed client. Always set a sane overall timeout (`Polly.Timeout` or `TimeoutPolicy`) so retries don't compound into unbounded latency for the caller, and log each retry attempt for observability. In Azure, Application Insights can track retry/circuit-breaker events to correlate downstream degradation with upstream latency spikes.

```csharp
services.AddHttpClient<IOrdersApiClient, OrdersApiClient>()
    .AddTransientHttpErrorPolicy(builder => builder.WaitAndRetryAsync(
        retryCount: 3,
        sleepDurationProvider: attempt => TimeSpan.FromSeconds(Math.Pow(2, attempt))))
    .AddTransientHttpErrorPolicy(builder => builder.CircuitBreakerAsync(
        handledEventsAllowedBeforeBreaking: 5,
        durationOfBreak: TimeSpan.FromSeconds(30)));
```

## Preventing lost updates when two users modify the same row simultaneously (optimistic concurrency control)
A lost update happens when two users read the same row, both make changes, and the second save silently overwrites the first user's changes without either being aware of the conflict. Optimistic concurrency control solves this without locking rows for the duration of a user's edit session (which would hurt scalability); instead, it detects conflicts only at save time. In SQL Server/EF Core, this is implemented with a `rowversion`/`timestamp` column (or a version number) that changes automatically every time the row is updated. EF Core includes the original version value in the `WHERE` clause of the `UPDATE` statement; if the row was already modified by someone else, zero rows match, EF Core throws a `DbUpdateConcurrencyException`, and the application can present a merge/retry UI instead of silently losing data. This is far more scalable than pessimistic locking (`SELECT ... WITH (UPDLOCK)`), which holds locks and risks deadlocks/timeouts under load, so optimistic concurrency is preferred for typical web applications with think-time between read and write. On conflict, options include: reload and let the user re-apply changes, perform a field-level merge, or reject with a clear "this record was updated by someone else" message. Always show the user the current server state on conflict rather than forcing a blind overwrite, and log conflicts to detect hot rows that might need a different concurrency strategy.

```csharp
public class Product {
    public int Id { get; set; }
    public string Name { get; set; }
    public decimal Price { get; set; }

    [Timestamp]
    public byte[] RowVersion { get; set; } // auto-managed concurrency token
}

try {
    await _context.SaveChangesAsync();
} catch (DbUpdateConcurrencyException) {
    return Conflict("This product was modified by another user. Please reload and try again.");
}
```

## Resolving slow search queries on a large table via composite indexing
When a query filters or sorts on multiple columns, a single-column index often isn't enough because SQL Server can only use it efficiently for the leading column, forcing a scan or an expensive key lookup for the rest. A composite (multi-column) index defined in the same order the query filters/sorts by lets the engine seek directly to the matching rows using all predicates at once. The column order matters: put the most selective, equality-filtered column first, followed by range-filtered columns, and finally include any additional columns the query only needs to read (not filter on) as `INCLUDE` columns to make the index "covering" and avoid a key lookup back to the clustered index entirely. Before adding an index, analyze the actual execution plan to confirm the bottleneck is a table/index scan or key lookup rather than something else like parameter sniffing or an outdated statistics. Composite indexes have a cost too — they slow down INSERT/UPDATE/DELETE and consume storage — so they should be added deliberately based on real query patterns (e.g., via `sys.dm_db_missing_index_details` or Query Store), not speculatively. Avoid indexing columns used with leading wildcards (`LIKE '%term%'`) since a B-tree index can't seek on them efficiently; a full-text index or trigram-based search may be more appropriate there. On Azure SQL, the built-in Query Performance Insight and automatic tuning can suggest and even auto-apply beneficial indexes.

```sql
-- Query filters by Status (equality) and sorts by CreatedDate (range),
-- and also needs CustomerName in the result set
SELECT OrderId, CustomerName, CreatedDate
FROM Orders
WHERE Status = 'Pending'
ORDER BY CreatedDate DESC;

CREATE NONCLUSTERED INDEX IX_Orders_Status_CreatedDate
ON Orders (Status, CreatedDate DESC)
INCLUDE (CustomerName);
```

## Protecting endpoints from XSS via unsanitized HTML input (e.g., HtmlSanitizer)
Cross-site scripting occurs when user-supplied content containing HTML/JavaScript (e.g., a rich-text comment or bio field) is stored and later rendered without sanitization, letting an attacker's script execute in another user's browser. The first line of defense is encoding output by default — Razor views in ASP.NET Core HTML-encode all `@Model` expressions automatically, so plain text fields are safe out of the box; the risk arises specifically when you intentionally render raw HTML via `Html.Raw()` or a frontend `dangerouslySetInnerHTML`/`innerHTML` for rich-text content. For those cases, sanitize the HTML on the server before storing or before rendering, using a library like `HtmlSanitizer` (Ganss.XSS) which whitelists safe tags/attributes (`<b>`, `<i>`, `<a href>`) and strips dangerous ones (`<script>`, `onerror`, `javascript:` URIs). Sanitize on write (before saving to the database) so the stored data is always safe, and optionally sanitize again on read as defense-in-depth in case sanitization rules change. Complement sanitization with a strict Content-Security-Policy header to block inline scripts even if something slips through, and set cookies as `HttpOnly` so stolen scripts can't read the session/auth cookie. Never rely on client-side sanitization alone since it can be bypassed by calling the API directly. Also validate/encode data going into HTML attributes, URLs, and JavaScript contexts differently, since each context has different encoding rules.

```csharp
using Ganss.Xss;

var sanitizer = new HtmlSanitizer();
sanitizer.AllowedTags.Clear();
sanitizer.AllowedTags.UnionWith(new[] { "b", "i", "a", "p" });
sanitizer.AllowedAttributes.UnionWith(new[] { "href" });

string safeHtml = sanitizer.Sanitize(userSubmittedHtml);
comment.Body = safeHtml; // store sanitized HTML, never the raw input
```

## Checking hierarchical direct reports' live status (e.g., "On Leave") in a manager dashboard query
A manager dashboard that shows the live status of all direct reports — potentially across multiple levels of a reporting hierarchy — needs a recursive query rather than a fixed number of joins, since org charts vary in depth. In SQL Server, this is solved with a recursive Common Table Expression (CTE): the anchor member selects direct reports of the given manager, and the recursive member joins the CTE back to the employee table on `ManagerId` to walk down additional levels until no more reports are found. Once the full set of subordinate `EmployeeId`s is resolved, join to a `Status`/`Attendance` table to pull each person's current status (e.g., "On Leave", "Active") — ideally this status table is indexed on `EmployeeId` and reflects the latest state rather than being computed from raw event logs on every request. For a dashboard queried frequently, consider caching the resolved hierarchy (it changes rarely) separately from the live status (which changes often), so you're not re-computing the recursive traversal on every page load — e.g., materialize the hierarchy nightly and just join against live status data per request. Guard against circular references in the `ManagerId` chain with a `MAXRECURSION` option to avoid infinite loops from bad data. Exposing this as a single API endpoint backed by a stored procedure or a well-indexed EF Core query with `FromSqlRaw` keeps the recursive logic in the database, where set-based traversal is efficient, rather than looping in application code.

```sql
WITH DirectReports AS (
    SELECT EmployeeId, ManagerId, 0 AS Level
    FROM Employees
    WHERE ManagerId = @ManagerId

    UNION ALL

    SELECT e.EmployeeId, e.ManagerId, dr.Level + 1
    FROM Employees e
    INNER JOIN DirectReports dr ON e.ManagerId = dr.EmployeeId
)
SELECT dr.EmployeeId, e.Name, s.CurrentStatus
FROM DirectReports dr
INNER JOIN Employees e ON e.EmployeeId = dr.EmployeeId
INNER JOIN EmployeeStatus s ON s.EmployeeId = dr.EmployeeId
OPTION (MAXRECURSION 50);
```

## Deduplicating conflicting attendance/agenda log entries using a priority hierarchy
When multiple sources feed overlapping records for the same entity/time slot (e.g., biometric attendance device, manual HR entry, and a mobile app check-in all logging the same day), naive deduplication by uniqueness alone loses information about which entry should "win" when they conflict. The solution is to define an explicit priority hierarchy for sources (e.g., biometric > manager override > mobile self check-in) and apply a window function to pick the highest-priority row per logical key (`EmployeeId`, `Date`). In SQL Server, `ROW_NUMBER()` partitioned by the logical key and ordered by a `CASE`-mapped source priority (and a tiebreaker like `CreatedAt DESC`) elegantly selects exactly one winning row per group, which is far more maintainable than nested `NOT EXISTS`/`MAX` subqueries. This logic should ideally run as part of an ingestion/ETL step (e.g., an Azure Function or scheduled job) that writes a clean, de-duplicated table for downstream reporting, rather than being recomputed ad hoc on every read. Keep the raw, unmodified logs in an audit table for traceability, and only the resolved view is used by dashboards — this preserves the ability to investigate disputes later. Document the priority rules with the business stakeholders, since "which source wins" is a domain decision, not a technical one, and it can change over time (requiring the mapping table/CASE statement to be data-driven rather than hardcoded).

```sql
WITH RankedEntries AS (
    SELECT *,
        ROW_NUMBER() OVER (
            PARTITION BY EmployeeId, LogDate
            ORDER BY
                CASE Source
                    WHEN 'Biometric' THEN 1
                    WHEN 'ManagerOverride' THEN 2
                    WHEN 'MobileApp' THEN 3
                    ELSE 99
                END,
                CreatedAt DESC
        ) AS Rank
    FROM AttendanceLogs
)
SELECT * FROM RankedEntries WHERE Rank = 1;
```

## Excel report download is slow for large datasets — how do you resolve it (e.g., streaming with MiniExcel)?
Slow Excel exports typically stem from building the entire workbook in memory (e.g., with `ClosedXML`/`EPPlus` loading all rows into an in-memory `IXLWorksheet` object) before writing it to the response, which spikes memory usage and delays the first byte sent to the client for large datasets. The fix is to switch to a streaming approach: query the database with a forward-only cursor (`IAsyncEnumerable`/`ToAsyncEnumerable`) instead of materializing the full result set with `ToList()`, and write rows to the output stream incrementally as they're read. `MiniExcel` is designed for exactly this — it uses SAX-style/streaming APIs to generate `.xlsx` files with minimal memory overhead, supporting `IEnumerable`/`IAsyncEnumerable` sources so rows are written to the response stream as they're produced rather than buffered entirely. On the API side, return the file via `FileStreamResult` writing directly to `HttpResponse.Body`, and ensure the underlying SQL query is properly indexed and paginated at the source (e.g., avoid `SELECT *` and unnecessary joins) so the bottleneck isn't actually the query itself. For very large exports (hundreds of thousands of rows), consider offloading generation to a background job (Azure Function/Hangfire) that writes the file to Blob Storage and emails/notifies the user a download link, rather than holding an HTTP request open for minutes. Compression (gzip) on the response and chunked transfer encoding further reduce time-to-first-byte and total transfer size.

```csharp
[HttpGet("export")]
public async Task ExportOrders() {
    Response.ContentType = "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet";
    Response.Headers.Add("Content-Disposition", "attachment; filename=orders.xlsx");

    var rows = _context.Orders
        .AsNoTracking()
        .Select(o => new { o.Id, o.CustomerName, o.Total })
        .AsAsyncEnumerable(); // streamed from SQL, not fully materialized

    await MiniExcel.SaveAsAsync(Response.Body, rows, excelType: ExcelType.XLSX);
}
```

## Resolve duplicate database records (data cleanup, unique constraints, idempotent API design, distributed locking)
Duplicate records usually originate from a missing uniqueness guarantee combined with retries, double-clicks, or concurrent requests racing past an application-level "check then insert" check. The permanent fix has two parts: first, clean up existing duplicates by identifying them with a `ROW_NUMBER()` partitioned over the natural key, keeping one canonical row (usually the earliest or most complete) and archiving/deleting the rest inside a transaction, ideally with a backup first. Second, and more importantly, add a database-level unique constraint/index on the natural key (e.g., `Email`, or `OrderNumber`) so duplicates become physically impossible going forward, regardless of application bugs. On the API side, make write operations idempotent by requiring an `Idempotency-Key` header (or client-generated GUID) that the server checks against a table of already-processed requests before inserting, so retried requests (e.g., from network timeouts) return the original result instead of creating a new record. For distributed scenarios with multiple app instances, a database unique constraint combined with catching the resulting `DbUpdateException`/constraint violation on the fly is usually sufficient and simpler than distributed locks (e.g., Redis `RedLock` or `SqlAppLock`), which should be reserved for coordinating longer-running, non-DB-enforceable critical sections. Always let the database be the final source of truth for uniqueness — application-level checks alone are inherently racy under concurrency.

```sql
-- Cleanup: keep the earliest row per duplicate key, remove the rest
WITH Duplicates AS (
    SELECT *, ROW_NUMBER() OVER (PARTITION BY Email ORDER BY CreatedAt) AS rn
    FROM Users
)
DELETE FROM Duplicates WHERE rn > 1;

-- Prevent future duplicates
ALTER TABLE Users ADD CONSTRAINT UQ_Users_Email UNIQUE (Email);
```
```csharp
[HttpPost("orders")]
public async Task<IActionResult> CreateOrder(OrderDto dto, [FromHeader] Guid idempotencyKey) {
    var existing = await _context.ProcessedRequests.FindAsync(idempotencyKey);
    if (existing != null)
        return Ok(existing.Result); // safe retry, no duplicate created

    var order = dto.ToEntity();
    _context.Orders.Add(order);
    _context.ProcessedRequests.Add(new ProcessedRequest { Id = idempotencyKey, Result = order.Id });
    await _context.SaveChangesAsync();
    return Ok(order.Id);
}
```

## Troubleshoot an API response-time increase (distributed tracing, DB performance, thread pool starvation, memory profiling)
A methodical approach starts with observability data rather than guessing: check Azure Application Insights for the affected endpoint's dependency breakdown (SQL calls, HTTP calls to other services, external APIs) to see whether the slowdown is in the database, a downstream dependency, or the app itself. Distributed tracing (OpenTelemetry/App Insights correlation IDs) lets you follow a single request across services to pinpoint exactly which hop introduced the latency, rather than treating the API as a black box. If the database is implicated, check for missing indexes, blocking/deadlocks, or a regressed execution plan (parameter sniffing) using `sys.dm_exec_requests`, Query Store, or the actual execution plan for the slow query. If dependency times look normal but the API itself is slow, thread pool starvation is a common culprit — caused by blocking async code (`.Result`/`.Wait()`) or too many concurrent synchronous calls exhausting available threads; check the `ThreadPool` queue length and pending work items via `.NET` counters or `dotnet-counters`. Memory pressure (frequent Gen2 GC pauses, or increasing memory over time indicating a leak) can also cause response-time spikes; a memory profiler (`dotnet-trace`, `dotnet-gcdump`, or Visual Studio's diagnostic tools) helps identify object retention issues, such as static collections growing unbounded or undisposed `HttpClient`/`DbContext` instances. Correlate the timing of the regression with recent deployments, config changes, or traffic growth to narrow the root cause quickly, and add alerts on p95/p99 latency so future regressions are caught before users report them.

```csharp
// Common cause of thread pool starvation: blocking on async code
public IActionResult GetData() {
    var result = _service.GetDataAsync().Result; // blocks a thread pool thread
    return Ok(result);
}

// Fix: make the whole call chain async
public async Task<IActionResult> GetData() {
    var result = await _service.GetDataAsync();
    return Ok(result);
}
```
