# MSSQL Interview Prep — 20 Queries (Simple → Advanced)

**Sample schema used throughout** (Northwind-style, assume these tables exist):

```sql
Employees(EmployeeID, FirstName, LastName, DepartmentID, ManagerID, Salary, HireDate)
Departments(DepartmentID, DepartmentName)
Orders(OrderID, CustomerID, EmployeeID, OrderDate)
OrderDetails(OrderID, ProductID, Quantity, UnitPrice)
Products(ProductID, ProductName, CategoryID, UnitPrice)
```

---

## 1. Basic filtering and sorting
**Concept:** `WHERE` filters rows before grouping; `ORDER BY` sorts the final result set. This is the most fundamental query pattern and almost always the warm-up question.

```sql
-- Get all employees hired after 2023, newest first
SELECT EmployeeID, FirstName, LastName, HireDate
FROM Employees
WHERE HireDate > '2023-01-01'   -- filter rows
ORDER BY HireDate DESC;          -- sort descending by hire date
```

---

## 2. DISTINCT
**Concept:** `DISTINCT` removes duplicate rows from the result set based on all selected columns. Interviewers use this to check you understand it operates on the whole row, not one column in isolation.

```sql
-- List each unique department that currently has employees
SELECT DISTINCT DepartmentID
FROM Employees;
```

---

## 3. Aggregate functions + GROUP BY
**Concept:** Aggregate functions (`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`) collapse multiple rows into one per group defined by `GROUP BY`.

```sql
-- Average salary per department
SELECT DepartmentID,
       COUNT(*)      AS EmployeeCount,   -- number of employees in the group
       AVG(Salary)   AS AvgSalary        -- average salary in the group
FROM Employees
GROUP BY DepartmentID;
```

---

## 4. WHERE vs HAVING
**Concept:** `WHERE` filters rows before aggregation; `HAVING` filters groups after aggregation. A classic "explain the difference" + code question.

```sql
-- Departments with more than 5 employees earning over 50,000
SELECT DepartmentID, COUNT(*) AS HighEarners
FROM Employees
WHERE Salary > 50000              -- row-level filter, applied first
GROUP BY DepartmentID
HAVING COUNT(*) > 5;              -- group-level filter, applied after grouping
```

---

## 5. INNER JOIN
**Concept:** Returns only rows that have matching values in both tables. The go-to join for combining related data.

```sql
-- Employee names with their department names
SELECT e.FirstName, e.LastName, d.DepartmentName
FROM Employees e
INNER JOIN Departments d
    ON e.DepartmentID = d.DepartmentID;  -- match on the shared key
```

---

## 6. LEFT JOIN to find unmatched rows
**Concept:** `LEFT JOIN` keeps all rows from the left table, filling in `NULL` for unmatched right-table columns. Combined with `IS NULL`, it's the standard pattern for "find rows with no related record."

```sql
-- Departments that have zero employees
SELECT d.DepartmentID, d.DepartmentName
FROM Departments d
LEFT JOIN Employees e
    ON d.DepartmentID = e.DepartmentID
WHERE e.EmployeeID IS NULL;   -- no matching employee row exists
```

---

## 7. Self JOIN
**Concept:** A table joined to itself, typically used for hierarchical or comparative relationships within the same table (e.g., employee-to-manager).

```sql
-- List each employee alongside their manager's name
SELECT emp.FirstName + ' ' + emp.LastName AS Employee,
       mgr.FirstName + ' ' + mgr.LastName AS Manager
FROM Employees emp
LEFT JOIN Employees mgr
    ON emp.ManagerID = mgr.EmployeeID;  -- ManagerID points back to EmployeeID
```

---

## 8. Correlated subquery
**Concept:** A subquery that references a column from the outer query, re-evaluated for each outer row. Commonly used to compare a row against an aggregate of its own group.

```sql
-- Employees earning more than the average salary of their own department
SELECT e.EmployeeID, e.FirstName, e.Salary, e.DepartmentID
FROM Employees e
WHERE e.Salary > (
    SELECT AVG(e2.Salary)
    FROM Employees e2
    WHERE e2.DepartmentID = e.DepartmentID   -- correlated: tied to outer row
);
```

---

## 9. EXISTS vs IN
**Concept:** `EXISTS` checks for the presence of any matching row and stops as soon as one is found (often faster on large sets, and safely handles NULLs); `IN` compares a value against a list. Interviewers like asking when to prefer one over the other.

```sql
-- Customers who have placed at least one order (using EXISTS)
SELECT c.CustomerID
FROM Customers c
WHERE EXISTS (
    SELECT 1
    FROM Orders o
    WHERE o.CustomerID = c.CustomerID   -- correlated existence check
);
```

---

## 10. UNION vs UNION ALL
**Concept:** `UNION` combines result sets and removes duplicates (implicit sort/dedupe cost); `UNION ALL` combines them and keeps all rows, which is faster when you know there's no overlap.

```sql
-- Combine current employees and archived employees into one list
SELECT EmployeeID, FirstName, LastName FROM Employees
UNION ALL                                   -- keep all rows, no dedupe overhead
SELECT EmployeeID, FirstName, LastName FROM ArchivedEmployees;
```

## 11. Nth highest value
**Concept:** A very common scenario question. `OFFSET-FETCH` (SQL Server 2012+) is the cleanest modern approach; older approaches use `TOP` with a subquery or ranking functions (see #12).

```sql
-- Find the 3rd highest salary
SELECT DISTINCT Salary
FROM Employees
ORDER BY Salary DESC
OFFSET 2 ROWS FETCH NEXT 1 ROWS ONLY;  -- skip top 2, take the next 1
```

---

## 12. Ranking window functions
**Concept:** `ROW_NUMBER`, `RANK`, and `DENSE_RANK` assign a position to each row within a partition. Key difference: `RANK` leaves gaps after ties, `DENSE_RANK` doesn't, `ROW_NUMBER` ignores ties entirely.

```sql
-- Rank employees by salary within each department
SELECT EmployeeID, DepartmentID, Salary,
       ROW_NUMBER() OVER (PARTITION BY DepartmentID ORDER BY Salary DESC) AS RowNum,
       RANK()       OVER (PARTITION BY DepartmentID ORDER BY Salary DESC) AS Rnk,
       DENSE_RANK() OVER (PARTITION BY DepartmentID ORDER BY Salary DESC) AS DenseRnk
FROM Employees;
```

## 13. Find duplicate rows
**Concept:** Group by the columns that define a "duplicate" and filter groups with more than one occurrence using `HAVING`.

```sql
-- Find duplicate employee entries (same first name, last name, hire date)
SELECT FirstName, LastName, HireDate, COUNT(*) AS Occurrences
FROM Employees
GROUP BY FirstName, LastName, HireDate
HAVING COUNT(*) > 1;   -- only groups appearing more than once
```

## 14. Common Table Expression (CTE)
**Concept:** A `WITH` clause defines a named, temporary result set that improves readability and lets you reference the same logic multiple times without repeating a subquery.

```sql
-- Use a CTE to first calculate department averages, then filter
WITH DeptAvg AS (
    SELECT DepartmentID, AVG(Salary) AS AvgSalary
    FROM Employees
    GROUP BY DepartmentID
)
SELECT e.EmployeeID, e.Salary, d.AvgSalary
FROM Employees e
JOIN DeptAvg d ON e.DepartmentID = d.DepartmentID
WHERE e.Salary > d.AvgSalary;   -- reuse the CTE result like a table
```

## 15. Recursive CTE
**Concept:** A CTE that references itself to walk hierarchical data (org charts, category trees, bill-of-materials). Consists of an "anchor" query and a "recursive" query joined with `UNION ALL`.

```sql
-- Build a full management chain starting from the CEO (ManagerID IS NULL)
WITH OrgChart AS (
    -- Anchor: top-level employees with no manager
    SELECT EmployeeID, FirstName, LastName, ManagerID, 0 AS Level
    FROM Employees
    WHERE ManagerID IS NULL

    UNION ALL

    -- Recursive: join each employee to their manager's row from OrgChart
    SELECT e.EmployeeID, e.FirstName, e.LastName, e.ManagerID, o.Level + 1
    FROM Employees e
    INNER JOIN OrgChart o ON e.ManagerID = o.EmployeeID
)
SELECT * FROM OrgChart
ORDER BY Level;
```

## 16. Running total with a window function
**Concept:** `SUM() OVER (ORDER BY ...)` computes a cumulative aggregate without collapsing rows, unlike `GROUP BY`. A frequent "analytics" interview question.

```sql
-- Running total of order amounts per customer, ordered by date
SELECT CustomerID, OrderID, OrderDate, TotalAmount,
       SUM(TotalAmount) OVER (
           PARTITION BY CustomerID       -- restart total per customer
           ORDER BY OrderDate            -- accumulate in date order
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS RunningTotal
FROM Orders;
```

## 17. PIVOT
**Concept:** Turns unique row values into columns, useful for turning long/normalized data into a cross-tab report. SQL Server has a native `PIVOT` operator.

```sql
-- Total quantity sold per product, one column per year
SELECT ProductID, [2024], [2025], [2026]
FROM (
    SELECT od.ProductID, YEAR(o.OrderDate) AS OrderYear, od.Quantity
    FROM OrderDetails od
    JOIN Orders o ON od.OrderID = o.OrderID
) AS SourceData
PIVOT (
    SUM(Quantity)                       -- aggregate to place in each new column
    FOR OrderYear IN ([2024], [2025], [2026])  -- values that become columns
) AS PivotTable;
```

## 18. MERGE (upsert)
**Concept:** `MERGE` combines insert, update, and delete logic into a single statement based on whether a matching row exists — the standard SQL Server way to do an "upsert."

```sql
-- Sync a Staging table into Products: update existing, insert new
MERGE Products AS target
USING StagingProducts AS source
    ON target.ProductID = source.ProductID
WHEN MATCHED THEN
    UPDATE SET target.ProductName = source.ProductName,   -- row exists: update it
               target.UnitPrice   = source.UnitPrice
WHEN NOT MATCHED BY TARGET THEN
    INSERT (ProductID, ProductName, UnitPrice)             -- row missing: insert it
    VALUES (source.ProductID, source.ProductName, source.UnitPrice);
```

## 19. Finding gaps in a sequence
**Concept:** A classic "gaps and islands" problem. Compare each row's value to what the previous row (via `LAG`) or an expected sequential value would be, to detect missing numbers or date breaks.

```sql
-- Find missing OrderIDs in an otherwise sequential range
WITH Numbers AS (
    SELECT MIN(OrderID) AS n FROM Orders
    UNION ALL
    SELECT n + 1 FROM Numbers WHERE n < (SELECT MAX(OrderID) FROM Orders)
)
SELECT n AS MissingOrderID
FROM Numbers
WHERE n NOT IN (SELECT OrderID FROM Orders)
OPTION (MAXRECURSION 0);   -- allow the recursive CTE to run past the 100-row default
```

## 20. Stored procedure with transaction and error handling
**Concept:** Wraps DML in `BEGIN TRAN` / `COMMIT` / `ROLLBACK` with `TRY...CATCH` so a multi-step operation either fully succeeds or fully rolls back — a common "senior-level" question testing production-safety habits.

```sql
CREATE PROCEDURE dbo.TransferBudget
    @FromDeptID INT,
    @ToDeptID   INT,
    @Amount     DECIMAL(10,2)
AS
BEGIN
    SET NOCOUNT ON;

    BEGIN TRY
        BEGIN TRANSACTION;

        -- Deduct from source department
        UPDATE Departments
        SET Budget = Budget - @Amount
        WHERE DepartmentID = @FromDeptID;

        -- Add to destination department
        UPDATE Departments
        SET Budget = Budget + @Amount
        WHERE DepartmentID = @ToDeptID;

        -- Guard against a source department going negative
        IF EXISTS (SELECT 1 FROM Departments WHERE DepartmentID = @FromDeptID AND Budget < 0)
            THROW 50000, 'Insufficient budget for transfer.', 1;

        COMMIT TRANSACTION;   -- both updates succeeded, make them permanent
    END TRY
    BEGIN CATCH
        IF @@TRANCOUNT > 0
            ROLLBACK TRANSACTION;   -- undo both updates on any error

        THROW;   -- re-raise the original error to the caller
    END CATCH
END;
```

### Tips for the interview itself
- Talk through your logic out loud before typing — interviewers weight reasoning as much as syntax.
- If a question is ambiguous (e.g., "find duplicates"), ask what defines a duplicate before writing code.
- Know the logical query processing order: `FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY` — it explains why you can't use a column alias in `WHERE` but can in `ORDER BY`.
- Be ready to explain execution plans and indexing basics (clustered vs. non-clustered) even if not asked to write code for them.
