## What is a Mutex?
A Mutex (mutual exclusion) is a synchronization primitive that ensures only one thread can access a protected resource or critical section at a time. In .NET, `System.Threading.Mutex` is a kernel-level object, meaning it can be used to synchronize access across multiple processes, not just threads within the same process — this makes it heavier-weight than a `lock`/`Monitor`, which is process-local only. A thread acquires the mutex by calling `WaitOne()` and releases it with `ReleaseMutex()`; if another thread already holds it, the calling thread blocks until it's released. Because it's an OS-level object, a named `Mutex` can be used to prevent multiple instances of an application from running simultaneously across the whole machine. Mutexes are reentrant by default in .NET only if the same thread that owns it calls `WaitOne()` again — but forgetting to release causes deadlocks, so `try/finally` is essential. Due to the overhead of crossing into kernel mode, a `Mutex` should be used only when cross-process synchronization is genuinely required; for in-process synchronization, `lock` (Monitor) or `SemaphoreSlim` are cheaper and preferred. On Azure, distributed equivalents like a blob lease or Redis-based `RedLock` play a similar mutual-exclusion role across multiple machines/instances.

```csharp
using var mutex = new Mutex(false, "Global\\MyAppSingleInstanceMutex");
if (!mutex.WaitOne(TimeSpan.Zero)) {
    Console.WriteLine("Another instance is already running.");
    return;
}
try {
    RunApplication();
} finally {
    mutex.ReleaseMutex();
}
```

## Is there any difference between a Binary Semaphore and Mutex?
Although both a binary semaphore and a mutex allow only one unit of access at a time, they differ in ownership semantics and intended use. A mutex has the concept of ownership — only the thread that acquired the lock is allowed to release it, and the runtime/OS can enforce this; a semaphore has no ownership, so any thread can call `Release()` on a `SemaphoreSlim`/`Semaphore`, even one that never called `Wait()`. This makes semaphores suitable for signaling between different threads (e.g., a producer signals a consumer), whereas a mutex is meant purely for protecting a critical section from concurrent access by the same conceptual "owner". A binary semaphore is essentially a semaphore with a maximum count of 1, functionally similar to a mutex for exclusion, but it's typically used for signaling scenarios rather than strict resource-locking. In .NET, `SemaphoreSlim` is the lightweight, in-process alternative to `Semaphore`, and it supports async waiting (`WaitAsync`), which a `Mutex` does not — making `SemaphoreSlim` the practical choice for throttling concurrent async operations. Mutexes can also support recursive (reentrant) acquisition by the owning thread, while binary semaphores generally don't track a specific owner and therefore don't support this pattern safely. Choosing between them comes down to whether you need strict ownership/reentrancy (mutex) or flexible signaling/throttling (semaphore).

```csharp
private static readonly SemaphoreSlim _semaphore = new SemaphoreSlim(1, 1); // binary semaphore

public async Task AccessResourceAsync() {
    await _semaphore.WaitAsync();
    try {
        // critical section, any caller (not just the one that waited) can release
    } finally {
        _semaphore.Release();
    }
}
```

## What is a Deadlock?
A deadlock is a state where two or more threads are permanently blocked because each is waiting on a resource held by another, and none can proceed. The classic cause is inconsistent lock ordering: Thread A locks Resource 1 then tries to lock Resource 2, while Thread B locks Resource 2 then tries to lock Resource 1 — each waits forever for the other to release. Deadlocks require four conditions to hold simultaneously (Coffman conditions): mutual exclusion, hold-and-wait, no preemption, and circular wait; breaking any one of them prevents deadlock. In .NET, deadlocks commonly arise from nested `lock` statements acquired in different orders across methods, or from blocking on async code (`.Result`/`.Wait()`) in a context with a captured `SynchronizationContext`, causing the continuation to never get scheduled. In SQL Server, deadlocks occur when two transactions acquire locks on rows/tables in an order that creates a circular dependency; SQL Server automatically detects this and kills the "victim" transaction (error 1205), letting the other proceed. Prevention strategies include enforcing a consistent global lock acquisition order, using timeouts (`Monitor.TryEnter`, `WaitOne(timeout)`) to fail fast rather than block indefinitely, and minimizing the scope/duration of locks. Detection tools include SQL Server's deadlock graph in Extended Events, and for .NET, thread dumps or `dotnet-dump` to inspect blocked threads and their wait chains.

```csharp
// Classic deadlock: inconsistent lock order across two threads
object lockA = new object();
object lockB = new object();

// Thread 1
lock (lockA) { lock (lockB) { /* ... */ } }

// Thread 2 (different order — causes deadlock under contention)
lock (lockB) { lock (lockA) { /* ... */ } }
```

## What is the difference between Concurrency and Parallelism?
Concurrency is about structuring a program so multiple tasks can make progress over the same time period, potentially by interleaving their execution on a single core — it's about dealing with many things at once, not necessarily doing them at once. Parallelism is about literally executing multiple tasks simultaneously on multiple CPU cores — it's about doing many things at once. A single-core machine can still be concurrent (e.g., an async web server switching between many in-flight requests while waiting on I/O) without ever being parallel, since only one instruction executes at any given instant. A multi-core machine running a `Parallel.For` loop across cores is both concurrent and parallel — many tasks are in progress and several are literally executing at the same instant. In .NET, `async`/`await` primarily targets concurrency for I/O-bound work (freeing threads while waiting rather than using more cores), while `Parallel.ForEach`, `PLINQ`, or `Task.Run` targets parallelism for CPU-bound work by spreading computation across the thread pool's cores. Choosing the right tool depends on whether the bottleneck is waiting (I/O-bound → concurrency/async) or computing (CPU-bound → parallelism). Both can be combined, e.g., processing multiple items in parallel where each item's processing is itself asynchronous.

```csharp
// Concurrency: many I/O-bound tasks in flight, not necessarily executing at once
await Task.WhenAll(urls.Select(u => httpClient.GetStringAsync(u)));

// Parallelism: CPU-bound work spread across cores
Parallel.For(0, data.Length, i => data[i] = Compute(data[i]));
```

## Explain the difference between Asynchronous and Parallel programming?
Asynchronous programming is about not blocking a thread while waiting for an operation to complete — typically an I/O operation like a database query, HTTP call, or file read — so that thread is freed to do other work in the meantime and resumes once the operation finishes. Parallel programming is about splitting CPU-bound work into pieces that run simultaneously across multiple threads/cores to finish the total computation faster. An `async` method calling `await httpClient.GetAsync(...)` doesn't use an extra thread while waiting for the network response — the calling thread returns to the thread pool and the continuation resumes on a (possibly different) thread pool thread once the response arrives. In contrast, `Parallel.Invoke` or `Task.Run` for CPU-bound work actively occupies multiple threads at the same time doing real computation, and adding more threads than CPU cores yields diminishing or negative returns. Mixing them up is a common mistake: using `Task.Run` to wrap I/O-bound work wastes a thread pool thread pointlessly holding a thread while waiting, whereas the natural `async`/`await` I/O APIs avoid that entirely. In an ASP.NET Core Web API, asynchronous programming (with `async`/`await` around EF Core/HTTP calls) is what allows a small number of threads to serve a very high number of concurrent requests, since most time is spent waiting on I/O rather than computing.

```csharp
// Asynchronous (I/O-bound): frees the thread while waiting on the DB
var orders = await _context.Orders.Where(o => o.IsActive).ToListAsync();

// Parallel (CPU-bound): actively uses multiple cores
var totals = orders.AsParallel().Select(o => ComputeTotal(o)).ToList();
```

## What is the meaning of the term "Thread-Safe"?
"Thread-safe" describes code or a data structure that behaves correctly when accessed by multiple threads concurrently, without producing corrupted state, exceptions, or inconsistent results. This usually means all shared mutable state is protected by synchronization (locks, semaphores, atomic operations) or the design avoids shared mutable state entirely (immutability, thread-local storage). A common misconception is that a class is automatically thread-safe just because individual method calls on it are atomic — composing multiple thread-safe operations (e.g., "check if key exists, then add it") is not itself atomic unless explicitly guarded, which is a classic source of subtle bugs. .NET's `System.Collections.Generic` types (like `List<T>`, `Dictionary<K,V>`) are explicitly not thread-safe for concurrent writes, while `System.Collections.Concurrent` types (`ConcurrentDictionary<K,V>`, `ConcurrentQueue<T>`) are designed to handle concurrent access safely with lock-free or fine-grained locking internally. Immutable types (like `record` or `string`) are inherently thread-safe since their state can't change after creation, eliminating the need for synchronization entirely. When documenting an API, being explicit about thread-safety guarantees (e.g., "instance members are not thread-safe; use one instance per thread") is important because callers cannot infer it just by reading the method signatures. In a Web API, thread-safety matters most for singleton-scoped services and static/shared caches, since those instances are shared across all concurrent requests.

```csharp
// Not thread-safe: check-then-act is not atomic
if (!_cache.ContainsKey(key)) _cache[key] = ComputeValue(); // race condition

// Thread-safe alternative
_cache.GetOrAdd(key, _ => ComputeValue()); // atomic add via ConcurrentDictionary
```

## What is a Race Condition?
A race condition occurs when the correctness of a program depends on the relative timing or interleaving of multiple threads accessing shared state, and different orderings produce different (and often incorrect) results. The classic example is two threads both reading a shared counter's current value, each incrementing their local copy, and writing it back — if both reads happen before either write, one increment is lost even though `count++` looks like a single operation. Race conditions are notoriously hard to reproduce and debug because they often only manifest under specific timing, load, or hardware conditions, and can pass every test run in a low-concurrency environment yet fail in production under real traffic. In .NET, race conditions are prevented by protecting shared mutable state with synchronization (`lock`, `Monitor`, `SemaphoreSlim`) or by using atomic operations (`Interlocked.Increment`) for simple counters. At the database level, the SQL Server equivalent is two transactions reading the same row and both computing an update based on stale data — solved with row locking (`UPDLOCK`), optimistic concurrency (`rowversion`), or `SELECT ... FOR UPDATE`-style isolation. A concrete example is two customers simultaneously buying the last unit of stock: without synchronization, both requests can read `Stock = 1`, both decrement, and both succeed, resulting in oversold inventory. Testing for race conditions typically requires stress/load testing with many concurrent requests rather than simple unit tests, since the bug is timing-dependent.

```csharp
private int _counter = 0;

// Race condition: count++ is read-increment-write, not atomic
public void UnsafeIncrement() => _counter++;

// Fix: atomic increment
public void SafeIncrement() => Interlocked.Increment(ref _counter);
```

## What's the difference between Deadlock and Livelock?
In a deadlock, threads are blocked and completely stop making progress — each is waiting indefinitely for a resource held by another, and nothing changes without external intervention. In a livelock, threads are not blocked — they're actively running and changing state in response to each other, but none of them makes real progress toward completing their work, effectively spinning in place. A common analogy is two people in a hallway both stepping aside to let the other pass, then both stepping back the same way at the same time, repeatedly — they're both busy and reacting, but neither gets through. In software, livelock can happen with overly "polite" retry/backoff logic: two threads detect a potential conflict, both back off and retry at the same interval, collide again, back off again, in an endless loop. Deadlock is usually easier to detect (threads are simply stuck, visible in a thread dump with a clear wait chain), whereas livelock is trickier because CPU usage stays high and threads appear "active" even though no useful work is completing. Fixing livelock typically involves adding randomized backoff (jitter) so competing threads don't retry in lockstep, or introducing a priority/tie-breaking rule so one side always wins the conflict. Both are failure modes of concurrent coordination logic, but livelock is a "busy" failure while deadlock is a "frozen" one.

## How much work should I place inside a lock statement?
A `lock` statement should protect the minimum amount of work necessary to keep a critical section correct — ideally just simple field reads/writes or short data-structure mutations, not I/O, network calls, or anything that can block for an unpredictable amount of time. Holding a lock while performing a database call, an HTTP request, or `await`ing another operation (which isn't even allowed directly inside a C# `lock` block) drastically increases the chance of contention, since every other thread waiting for that lock is now blocked for however long that slow operation takes. A good rule of thumb: locks should guard "compute and update in-memory state," not "do work" — perform expensive computation or I/O outside the lock, then briefly acquire the lock only to read/write the shared result. Long-held locks also increase the risk of deadlocks, since the window during which two locks might be held simultaneously grows, and increase tail latency for all other threads contending for that same lock under load. If asynchronous operations must be coordinated, use `SemaphoreSlim.WaitAsync()`/`Release()` instead of `lock`, since `lock` cannot wrap an `await` (the compiler disallows it) precisely because holding a thread-affine lock across an asynchronous suspension point is dangerous and easy to get wrong. As a general guideline, keep the code inside a lock short enough that you could describe it in one sentence — "increment a counter," "add an item to a list," not "call the payment gateway and update three tables."

```csharp
// Bad: holds the lock during a slow/blocking operation
lock (_lock) {
    var result = CallExternalApi(); // blocks everyone waiting on _lock
    _cache[key] = result;
}

// Good: do slow work outside the lock, keep the critical section tiny
var result = CallExternalApi();
lock (_lock) {
    _cache[key] = result;
}
```

## Write a function that guarantees to never return the same value twice
The simplest thread-safe way to guarantee uniqueness across calls, even under concurrent access, is an atomically incremented counter using `Interlocked.Increment`, which performs the increment as a single indivisible CPU instruction so no two threads can ever receive the same resulting value. For distributed scenarios spanning multiple processes or machines (not just threads in one process), a single in-memory counter isn't enough — you'd need a database identity column/sequence, a GUID (`Guid.NewGuid()`, which is practically globally unique without coordination), or a centralized counter service (e.g., Redis `INCR`, which is atomic across all connected clients). `Interlocked.Increment` is preferred over wrapping a plain `int++` in a `lock` because it avoids lock overhead entirely, using hardware-level atomic instructions, making it both simpler and faster for this specific use case. If a random unique value is acceptable rather than a sequential one, `Guid.NewGuid()` requires no shared state or coordination at all and works trivially across threads, processes, and machines. In a SQL Server-backed system, an `IDENTITY` column or `SEQUENCE` object provides the same atomic, never-repeating guarantee at the database level for records inserted concurrently by multiple app instances.

```csharp
private static long _lastValue = 0;

public static long GetNextUniqueValue() => Interlocked.Increment(ref _lastValue);
```

## What is Starvation?

Starvation occurs when a thread is perpetually denied access to a resource it needs to make progress, even though it's not technically deadlocked — other threads keep "cutting in line" ahead of it, so it waits indefinitely despite the resource periodically being available. This commonly happens with unfair scheduling or locking strategies: if a lock implementation always favors newly arriving threads over ones that have been waiting longest, a particular thread can be repeatedly bypassed forever. It can also arise from thread priority misconfiguration — if high-priority threads are always ready to run, a low-priority thread on a system without fair scheduling may never get CPU time. In ASP.NET Core, thread pool starvation is a very concrete, common form: if many requests block synchronously (e.g., calling `.Result` on a `Task`) instead of using `await`, the thread pool's limited worker threads all become occupied, and new incoming requests queue up waiting for a thread to free, causing severe latency spikes or timeouts under load. The fix for thread pool starvation is consistently using `async`/`await` throughout the call chain so threads are released back to the pool while waiting on I/O, rather than held hostage by blocking calls. Fair locking primitives (like a strictly FIFO queue-based lock) or explicit request queuing with fairness guarantees can prevent starvation in custom concurrency code. Monitoring thread pool queue length and the `ThreadPool.PendingWorkItemCount` (via `.NET` performance counters) helps detect starvation in production before it causes an outage.

## How does Async/Await prevent Thread Pool starvation?
Thread pool starvation happens when all available worker threads are occupied doing nothing but waiting (blocked) on a slow operation, leaving no threads free to handle new incoming work, so the entire application queues up and response times spike. `async`/`await` prevents this because, when an `await`ed operation is I/O-bound (a database call, HTTP request, file read), the underlying implementation doesn't hold the thread hostage — the current thread is released back to the thread pool immediately, and only when the I/O completion callback fires does a (possibly different) thread pool thread pick up the continuation to resume the method. This means a single thread pool with, say, 50 threads can service thousands of concurrent in-flight requests, since at any given moment only the requests actively doing CPU work are occupying threads — all the ones waiting on I/O aren't consuming a thread at all. The opposite — calling `.Result` or `.Wait()` on a task, or using `Thread.Sleep` for a delay — blocks a thread pool thread for the entire duration of the wait, actively starving the pool since that thread can't serve any other request in the meantime. This is why ASP.NET Core Web APIs universally use `async` controller actions with `await` all the way down to the database/HTTP calls: it decouples "number of concurrent requests" from "number of threads needed," which is essential for scalability. Under sustained blocking-call load, you'd see the thread pool try to compensate by injecting new threads (at a throttled rate, roughly one every couple of seconds), which is far slower than the near-instant thread release that proper async I/O provides — explaining why blocking calls cause visible latency spikes under load rather than an immediate crash.

```csharp
// Starves the thread pool under load: blocks a worker thread for the DB round-trip
public IActionResult GetOrders() => Ok(_context.Orders.ToList());

// Frees the thread while waiting on I/O, no thread held during the DB call
public async Task<IActionResult> GetOrdersAsync() => Ok(await _context.Orders.ToListAsync());
```

## What is a Data Race?

A data race is a specific, narrower condition than a general race condition: it occurs when two or more threads access the same memory location concurrently, at least one of those accesses is a write, and there is no synchronization establishing a happens-before ordering between them. Unlike a race condition (a logical/timing bug that can exist even with synchronization present, e.g., check-then-act patterns), a data race is specifically about unsynchronized concurrent memory access, and in many languages (including C/C++) it's classified as undefined behavior at the language/memory-model level, not just "the wrong logical outcome." In .NET, the memory model guarantees some behavior even without synchronization, but reading/writing a non-volatile, non-atomic shared field from multiple threads without a `lock`, `volatile`, or `Interlocked` can still produce torn reads/writes (particularly for types larger than a native word size) or reordering effects not visible in the source code order. Every data race is technically a race condition in the general sense, but not every race condition is a data race — a race condition can occur purely at the logical/business level (e.g., two transactions both approving the same request) even when every individual memory access is perfectly synchronized. Tools like the `.NET` `ThreadSanitizer`-style analyzers or careful code review are needed to catch data races, since they don't always manifest as visible incorrect output — sometimes the symptom is a crash from a torn read producing an invalid object state. The fix is always the same category of tool: proper synchronization (locks, `Interlocked`, `volatile` for simple flags) or eliminating shared mutable state via immutability or thread-local data.

## Provide some real-live examples of Livelock
A common real-world analogy is two people approaching each other in a narrow hallway: both step to their left to let the other pass, realize they're still blocking each other, both step to their right, and this repeats indefinitely — both are actively moving and reacting, but neither makes progress toward walking past the other. In networking, two nodes on a shared medium can detect a data collision, both back off for an identical fixed delay, then both retransmit at exactly the same moment again, colliding repeatedly forever — this is why real protocols use randomized/exponential backoff with jitter to break the symmetry. In software with optimistic concurrency, if two threads each detect a version conflict on retry and both immediately retry at the same instant using the exact same retry strategy, they can keep colliding on every attempt without any jitter, technically a livelock even though CPU usage looks "busy" and healthy from a monitoring dashboard. Another example is two processes trying to acquire two locks in opposite order but with "polite" logic that releases and retries whenever a conflict is detected instead of blocking — both keep releasing and re-acquiring in a synchronized dance, making no forward progress. The fix across all these examples is the same principle: break the symmetry, typically via randomized delays (jitter), a priority/tie-breaking rule so one side always wins, or switching from "detect and retry" logic to blocking with a defined wait order.

## What is Green Thread?
A green thread is a thread that is scheduled and managed by a language runtime or user-space library rather than by the operating system kernel, making it far cheaper to create and switch between than a native OS thread. Because the runtime (not the OS scheduler) controls when a green thread yields, thousands of them can be multiplexed onto a small number of actual OS threads, dramatically reducing memory overhead (each OS thread typically reserves at least 1MB of stack) and context-switch cost. .NET doesn't use classic green threads for its `Task`/`async` model in the same way languages like Go (goroutines) or Erlang do, but conceptually `Task`s scheduled on the thread pool serve a similar purpose: many logical units of work (tasks) are multiplexed onto a much smaller pool of real OS threads, especially for I/O-bound `async` continuations which don't need a dedicated thread while waiting. The key benefit of green threads/lightweight tasks is scalability — an application can have tens of thousands of concurrent "logical threads of execution" in flight without the memory and scheduling overhead that the same number of real OS threads would require. The tradeoff is that a green thread performing CPU-bound, non-yielding work can block the underlying OS thread it's currently multiplexed on, potentially starving other green threads sharing that same OS thread — which is analogous to why blocking calls inside `async` code in .NET are discouraged, since they hold onto a thread pool thread that could otherwise service other queued work. Understanding this model explains why `async`/`await` in .NET, despite not being "green threads" in the strictest sense, achieves similar scalability benefits for I/O-bound workloads by minimizing the number of OS threads required to handle massive concurrency.

## What are some advantages of Lockless Concurrency?
Lockless (lock-free) concurrency avoids traditional mutual-exclusion locks, instead relying on atomic CPU instructions (like compare-and-swap) to coordinate access to shared state, which eliminates several classes of problems that locks introduce. First, it removes the possibility of deadlock entirely for that data structure, since there's no lock to be held while waiting for another lock — there's simply no blocking wait at all. Second, it typically offers better throughput and scalability under high contention, since threads don't pay the cost of context-switching in and out of a blocked/waiting state, and there's no risk of one slow thread (e.g., preempted while holding a lock) stalling every other thread that needs the same resource (a problem called priority inversion or convoying). Third, it avoids the overhead of kernel-mode transitions that heavier synchronization primitives (like `Mutex`) can incur, since atomic instructions like `Interlocked.CompareExchange` execute entirely in user mode. In .NET, `System.Collections.Concurrent` types like `ConcurrentQueue<T>` and `ConcurrentStack<T>` are largely lock-free internally, offering much better scalability than wrapping a regular `Queue<T>` in a `lock` under heavy multi-threaded use. The tradeoff is complexity: lock-free algorithms are notoriously difficult to design correctly, prone to subtle bugs like the ABA problem, and are typically only worth hand-rolling for narrow, performance-critical scenarios — most application code should prefer the well-tested, battle-hardened concurrent collections rather than writing custom lock-free structures. Lock-free code also doesn't automatically mean "wait-free" — a thread can still theoretically retry its compare-and-swap loop many times under extreme contention, though it will never be blocked indefinitely by another thread holding a lock.

```csharp
private int _value;

// Lock-free increment using a compare-and-swap retry loop
public void LockFreeIncrement() {
    int initial, computed;
    do {
        initial = _value;
        computed = initial + 1;
    } while (Interlocked.CompareExchange(ref _value, computed, initial) != initial);
}
```

## Compare Actor Model with Threading Model for concurrency
The traditional threading model relies on shared mutable state protected by locks, semaphores, or other synchronization primitives — multiple threads directly read and write the same memory, and correctness depends on carefully coordinating that access, which is a well-known source of deadlocks, race conditions, and hard-to-reproduce bugs. The Actor Model instead eliminates shared mutable state entirely: each "actor" owns its private state exclusively, and the only way to interact with it is by sending it asynchronous messages, which the actor processes one at a time from its own mailbox/queue — since only the actor itself ever touches its state, there's no need for locks at all. This makes actor-based systems inherently easier to reason about at scale, since you no longer need to worry about interleaving of reads/writes to shared memory; the only concurrency concern becomes message ordering and delivery guarantees, which is a fundamentally simpler problem. In .NET, actor-style concurrency can be implemented with `System.Threading.Channels` (a producer/consumer queue) or frameworks like Akka.NET/Orleans (Microsoft's own actor framework, heavily used in Azure), where "grains" (Orleans' term for actors) handle one message at a time with no risk of concurrent access to their own state. The threading model tends to perform better for tightly-coupled, CPU-bound parallel work with low communication overhead (e.g., `Parallel.For` over an array), while the actor model shines for distributed, message-driven systems with many independent, loosely-coupled units of state (e.g., one actor per connected user session, or per IoT device). Actors also naturally map to distributed systems, since messages can be routed across process/machine boundaries transparently, whereas raw threads and locks are inherently confined to a single process. The main tradeoff of the actor model is the overhead of message passing (serialization, queuing, potential added latency), so it's not universally faster than tightly synchronized threading, just structurally safer for many concurrency scenarios.

## Two customers add a product to the basket in the same time whose the stock was only one (1). What will you do?
This is a classic race condition on limited inventory: both requests read `Stock = 1` at nearly the same instant, both think they can proceed, and without protection both decrements succeed, resulting in overselling by one unit. The most robust fix is to enforce the check-and-decrement atomically at the database level rather than in application code — a single `UPDATE Products SET Stock = Stock - 1 WHERE ProductId = @Id AND Stock > 0` statement is atomic in SQL Server: only one of the two concurrent transactions will actually find `Stock > 0` still true and successfully update a row, while the other affects zero rows and can be told "out of stock" based on the rows-affected count. This approach avoids a separate "read stock, check in app code, then write" sequence, which is exactly the racy check-then-act pattern that causes the bug in the first place. For higher-throughput or more complex reservation logic (e.g., a temporary "hold" while the customer completes checkout), a dedicated reservation table with a unique constraint per unit, or an application-level distributed lock (Redis `RedLock`) around the specific product, adds an extra layer of safety at the cost of complexity. Wrapping the update in a database transaction with an appropriate isolation level (Read Committed is sufficient here because the atomic `UPDATE ... WHERE` handles the race, not the isolation level itself) ensures the operation is durable and consistent. On the application side, whichever request's `UPDATE` affects zero rows should return a clear "out of stock" response to that customer rather than a generic error, so the frontend can react appropriately (e.g., prompt to remove the item from their basket).

```sql
UPDATE Products
SET Stock = Stock - 1
WHERE ProductId = @ProductId AND Stock > 0;

-- Check @@ROWCOUNT (or rows affected in ADO.NET/EF) to know if this request won the race
IF @@ROWCOUNT = 0
    THROW 51000, 'Product is out of stock', 1;
```

## How would you make an in-memory dictionary used as a feature-flag cache thread-safe, especially during a background sync?
A plain `Dictionary<TKey, TValue>` is not thread-safe for concurrent reads during writes, and a background sync job that periodically refreshes flags from a database/config service while requests are simultaneously reading flags is exactly the scenario that exposes this — you can get exceptions (`InvalidOperationException: Collection was modified`) or, worse, silently corrupted internal state. The simplest safe fix is switching to `ConcurrentDictionary<TKey, TValue>`, which is designed for exactly this pattern: many concurrent readers and occasional writers, using fine-grained internal locking/lock-free reads so readers are never blocked by a writer updating a different key. For a full-cache refresh (not just individual key updates), a better pattern than mutating the existing dictionary in place is to build a brand-new dictionary with the freshly synced data, then atomically swap the reference using `Interlocked.Exchange` (or simply reassigning a `volatile`/immutable reference) — readers always see either the fully-old or fully-new snapshot, never a partially-updated one. This "build new, swap reference" approach also avoids holding any lock during reads at all, since reading a reference is inherently atomic in .NET, making it extremely fast for the hot path (flag lookups on every request). If individual flags need in-place updates rather than full replacement, `ConcurrentDictionary.AddOrUpdate` handles the per-key race safely. It's important that the background sync task itself doesn't overlap with a previous still-running sync (guarded with a `SemaphoreSlim` or a simple "is running" flag) to avoid two syncs racing to swap the reference in an unpredictable order.

```csharp
private volatile IReadOnlyDictionary<string, bool> _flags = new Dictionary<string, bool>();

public bool IsEnabled(string flag) => _flags.TryGetValue(flag, out var enabled) && enabled;

public void SyncFromSource(IDictionary<string, bool> freshFlags) {
    // build a full new snapshot, then swap the reference atomically
    _flags = new Dictionary<string, bool>(freshFlags);
}
```

## What happens if you mix async and sync methods in one orchestrator and skip an await?
If an orchestrator method calls an `async` method but forgets the `await` keyword (a "fire-and-forget" call, e.g., `DoWorkAsync();` instead of `await DoWorkAsync();`), the orchestrator continues executing immediately without waiting for that operation to complete, and any exception thrown inside the un-awaited task is never observed by the caller — it can be silently swallowed or, in older .NET versions, crash the process asynchronously via the `UnobservedTaskException` event. This is particularly dangerous when the orchestrator's next lines of code assume the skipped operation already finished (e.g., reading a value the async call was supposed to write), leading to subtle bugs where behavior seems to work "most of the time" because the async operation often finishes before the next line executes, but fails intermittently under load or with slower dependencies. Mixing synchronous and asynchronous calls in the same orchestrator also risks reintroducing blocking behavior if a developer "fixes" a compiler warning by calling `.Result`/`.Wait()` on the task instead of properly awaiting it — this defeats the entire purpose of async and can cause thread pool starvation or even deadlock if a `SynchronizationContext` is present (classic ASP.NET, not ASP.NET Core, or WPF/WinForms UI threads). The safe practice is to make the orchestrator itself `async` end-to-end and await every call in the correct sequence, or explicitly and intentionally track fire-and-forget tasks (e.g., via a background task queue with its own exception handling) rather than accidentally dropping the `await`. Static analysis (the `CS4014` compiler warning "because this call is not awaited...") should never be suppressed without a deliberate, documented reason. In an orchestrator that legitimately needs to kick off some work without waiting (e.g., a non-critical audit log write), that intent should be explicit and paired with its own error handling, not just an accidentally-missing `await`.

```csharp
public async Task ProcessOrderAsync(Order order) {
    SendConfirmationEmailAsync(order); // BUG: missing await — fire-and-forget, exceptions lost
    await _context.SaveChangesAsync();  // may run before/without waiting for the email call
}

// Fix: await it, or explicitly track it as a deliberate background operation
public async Task ProcessOrderAsyncFixed(Order order) {
    await SendConfirmationEmailAsync(order);
    await _context.SaveChangesAsync();
}
```

## How do you avoid deadlocks when migrating a legacy synchronous API to async without changing method signatures immediately?
Migrating incrementally without changing public method signatures is risky because calling `.Result` or `.GetAwaiter().GetResult()` on a `Task` from a synchronous method, when that task's continuation needs to resume on the original captured `SynchronizationContext` (classic ASP.NET MVC, WPF, WinForms), causes a classic deadlock: the sync method blocks the context's only thread waiting for the task, while the task's continuation is waiting for that same thread to become free — neither ever proceeds. The safest incremental technique is to call `ConfigureAwait(false)` throughout the new async code path being introduced, which tells the awaited task's continuation not to try to resume on the original captured context, letting it run on any available thread pool thread instead and breaking the circular wait. In ASP.NET Core specifically, there's no `SynchronizationContext` by default, so this specific deadlock doesn't occur — but blocking with `.Result` still risks thread pool starvation under load even without a hard deadlock, so it should still be avoided or minimized. A pragmatic phased migration approach is: convert the lowest-level I/O calls to truly async first, temporarily expose both a sync-blocking wrapper (with `ConfigureAwait(false)` inside) and the new async method side-by-side, then gradually migrate callers to the async version and delete the sync wrapper once nothing depends on it. Never mix `.Result`/`.Wait()` with code that also needs the original context (e.g., HttpContext access patterns in old ASP.NET) — if legacy constraints truly require staying synchronous at the boundary, isolate the blocking call to the outermost layer only, and keep everything beneath it consistently async. Load-testing the migrated path specifically for thread pool exhaustion (not just functional correctness) is important, since deadlock avoidance doesn't automatically mean the migration is performant.

```csharp
// Legacy synchronous method signature kept temporarily during migration
public User GetUser(int id) {
    // ConfigureAwait(false) avoids deadlock risk from a captured SynchronizationContext
    return GetUserAsync(id).ConfigureAwait(false).GetAwaiter().GetResult();
}

public async Task<User> GetUserAsync(int id) {
    return await _context.Users.FindAsync(id).ConfigureAwait(false);
}
```

## What is the difference between Race Condition and Data Races? Are they the same?
They are related but not the same: a data race is a specific technical condition — two threads concurrently accessing the same memory location with at least one write and no synchronization establishing ordering between them — while a race condition is a broader, more general term for any bug where the program's correctness depends on the unpredictable timing/interleaving of operations. Every data race is a form of race condition, but a race condition can exist without any data race at all if it happens at a purely logical level, even when every individual memory access is properly synchronized — for example, two separate, individually-locked database transactions that each check "is there remaining stock" and both proceed based on stale information read a moment apart is a race condition in outcome, without any single unsynchronized memory access to point to as a "data race". Conversely, code can have a data race (unsynchronized concurrent memory access) that happens to never produce an observably wrong result in a given run, especially on architectures with strong memory ordering, yet is still, strictly speaking, undefined behavior in memory-model terms and a latent bug waiting to surface. In practice, when interviewers ask this, the key distinguishing point to make is: data races are about unsynchronized concurrent memory access (a low-level, mechanical definition), while race conditions are about incorrect behavior caused by timing dependencies (a higher-level, outcome-based definition) — the terms are often used interchangeably in casual conversation, but they're not formally identical. Fixing a data race requires adding synchronization or eliminating shared mutable memory; fixing a race condition might require synchronization too, but could also require redesigning the business logic (e.g., making the check-and-act sequence atomic at the database level) even when there's no raw memory race to speak of.

## What happens if you have a "race condition" on the lock itself?
This scenario typically describes a check-then-lock pattern (sometimes mistakenly used for "lazy initialization") where a thread checks a condition, and only if it's false, acquires a lock and creates/assigns something — without re-checking the condition after acquiring the lock, this "double-checked locking" pattern is unsafe if done incorrectly, because multiple threads can pass the initial unsynchronized check simultaneously before any of them has entered the lock, all queue up on the lock, and then all proceed to (re-)initialize the object one after another, undermining the "only once" guarantee. The proper fix for double-checked locking in .NET is to re-check the condition again inside the lock (the actual "double check"), so only the first thread that gets the lock actually performs the initialization, and every other thread that queued up behind it sees the now-true condition and skips redundant work. Additionally, the memory model matters here: without `volatile` or a proper memory barrier on the field being checked, a thread outside the lock could observe a partially-constructed object due to instruction reordering, even if the assignment appears to happen "after" the lock in source order — this was a real, subtle historical bug in naive double-checked locking implementations in C/C++ and early .NET. In modern .NET, this entire pattern is best avoided altogether by using `Lazy<T>` (with `LazyThreadSafetyMode.ExecutionAndPublication`), which handles all of this correctly and safely internally, so the recommendation in an interview is almost always "don't hand-roll this — use `Lazy<T>` or a similar built-in primitive." If the "race on the lock itself" instead refers to contention on `Monitor.Enter`/`lock` under heavy load (many threads simultaneously trying to acquire the same lock), that's not a bug — it's expected serialized contention, and the concern there shifts to minimizing time held inside the lock and avoiding priority inversion, rather than correctness.

```csharp
private static readonly Lazy<ExpensiveResource> _resource =
    new Lazy<ExpensiveResource>(() => new ExpensiveResource(), LazyThreadSafetyMode.ExecutionAndPublication);

public ExpensiveResource GetResource() => _resource.Value; // thread-safe, initialized exactly once
```
