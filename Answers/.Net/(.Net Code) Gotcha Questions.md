# C# / .NET Interview Prep — 20 Trap / "Gotcha" Questions

These aren't algorithm puzzles — they're the questions interviewers use to see whether
you understand *why* C# behaves the way it does, not just whether you can recite a
definition. Format for each: the trap, what actually happens and why, the fix, and the
underlying concept so you can generalize it to variations of the same question.

---

## 1. `async void` swallows exceptions

**Trap:**
```csharp
public async void SaveAsync()
{
    throw new InvalidOperationException("DB write failed");
}

try
{
    SaveAsync();       // looks like a normal call
    Console.WriteLine("Saved");
}
catch (Exception ex)
{
    Console.WriteLine("Caught: " + ex.Message);  // never runs
}
```
**What actually happens:** "Saved" prints, then the app crashes (or the exception
disappears, depending on host) — the `catch` block never fires.

**Why:** An `async void` method has no `Task` for the caller to hold on to. Under the
hood, `async` methods post their exception onto the `SynchronizationContext` (or, if
there isn't one, it re-throws on the thread pool and can crash the process) instead of
into a `Task` object the caller can observe. There is nothing to `await`, so there is
nothing to `catch`.

**Fix:** Return `Task` instead of `void`, and `await` it:
```csharp
public async Task SaveAsync() => throw new InvalidOperationException("DB write failed");

try { await SaveAsync(); }
catch (Exception ex) { Console.WriteLine("Caught: " + ex.Message); }
```
**Concept to generalize:** `async void` should exist *only* for event handlers, where the
delegate signature forces `void` and there's no caller to `await` it anyway. Anywhere
else — services, business logic, background work — it's a bug waiting to happen.

## 2. Deadlock from blocking on an async call

**Trap:**
```csharp
// Inside an ASP.NET (classic) controller action or WPF UI event handler:
public IActionResult Get()
{
    var data = FetchDataAsync().Result;  // blocks the calling thread
    return Ok(data);
}

public async Task<string> FetchDataAsync()
{
    await Task.Delay(1000);   // simulate I/O
    return "done";
}
```
**What actually happens:** The request hangs forever (or until a timeout kills it).

**Why:** `.Result` blocks the current thread until the task completes. By default,
`await` captures the current `SynchronizationContext` and resumes on it. In contexts
that only allow one thread at a time (classic ASP.NET request context, WPF/WinForms UI
thread), that thread is the one blocked on `.Result` — so the continuation can never get
back onto it to finish. Two things are waiting on each other: classic deadlock.

**Fix:** `await` all the way up the call stack instead of blocking:
```csharp
public async Task<IActionResult> Get()
{
    var data = await FetchDataAsync();
    return Ok(data);
}
```
If you truly must block (e.g., in a console app's `Main` before C# 7.1 top-level
`async Main` existed), use `ConfigureAwait(false)` inside the library code so
continuations don't try to resume on the captured context.

**Concept to generalize:** "Sync-over-async" (`.Result`, `.Wait()`, `GetAwaiter().GetResult()`
on a hot path) is a code-smell interviewers specifically look for. ASP.NET Core doesn't
have the classic `SynchronizationContext`, so this deadlock is less common there — but
the *pattern* of mixing sync and async is still considered wrong because it wastes
thread-pool threads and hides bugs that reappear under load.

## 3. LINQ is a recipe, not a result (deferred execution)

**Trap:**
```csharp
var numbers = new List<int> { 1, 2, 3 };
var query = numbers.Where(n => n > 1);   // "what does this line do?"

numbers.Add(4);
numbers.Add(5);

Console.WriteLine(query.Count());   // what prints?
```
**What actually happens:** It prints `4`, not `2` — even though `query` looks like it
was captured back when the list only had `{1,2,3}`.

**Why:** Most LINQ operators (`Where`, `Select`, `OrderBy`, etc.) are lazy. Calling
`.Where(...)` doesn't loop over anything — it builds an iterator (technically a
compiler-generated state machine) that stores the *source* and the *predicate*, and only
runs when something enumerates it (`foreach`, `ToList()`, `Count()`, `First()`, etc.).
Because `query` still just holds a reference to `numbers`, it sees every later mutation.

**Fix:** Force immediate execution to snapshot the state at that point in time:
```csharp
var snapshot = numbers.Where(n => n > 1).ToList();
```
**Concept to generalize:** This is also why the *same* query object can silently return
different results if it's enumerated twice with mutable source data in between — and why,
with EF Core, deferred execution is what lets a whole LINQ chain get translated into a
single SQL statement only when you finally enumerate it.

## 4. Multiple enumeration of `IEnumerable<T>`

**Trap:**
```csharp
IEnumerable<int> GetRandomNumbers()
{
    var rnd = new Random();
    for (int i = 0; i < 3; i++)
        yield return rnd.Next(100);
}

var numbers = GetRandomNumbers();
Console.WriteLine(numbers.Count());     // enumerates once
Console.WriteLine(numbers.First());     // enumerates AGAIN — different values!
```
**What actually happens:** `Count()` and `First()` each re-run the entire iterator from
scratch, so `First()` doesn't necessarily match what was counted, and if the source were
a database call it would hit the DB twice.

**Why:** `IEnumerable<T>` on its own doesn't cache anything — each foreach/LINQ terminal
operation calls `GetEnumerator()` again and walks the sequence from the start. If the
underlying data source is expensive (DB query, web call) or non-deterministic (`Random`,
`DateTime.Now`), every enumeration can produce a different — or expensive — result.

**Fix:** Materialize once if you need to use the sequence more than once:
```csharp
var numbers = GetRandomNumbers().ToList();
Console.WriteLine(numbers.Count);
Console.WriteLine(numbers[0]);
```
**Concept to generalize:** Treat any `IEnumerable<T>` you didn't just create yourself as
"read once" unless you know its source is a cheap, deterministic in-memory collection.
This is a frequent root cause of duplicate database round-trips in real EF Core code.

## 5. Captive dependency: singleton holding a scoped service

**Trap:**
```csharp
builder.Services.AddDbContext<AppDbContext>();      // Scoped by default
builder.Services.AddSingleton<ICacheWarmer, CacheWarmer>();

public class CacheWarmer : ICacheWarmer
{
    private readonly AppDbContext _db;
    public CacheWarmer(AppDbContext db) => _db = db;   // injected once, at app startup
}
```
**What actually happens:** In Development, the DI container throws at startup
("Cannot consume scoped service... from singleton"). In Production (where scope
validation is off by default), it silently works — but `_db` is the *same* `DbContext`
instance shared by every request forever.

**Why:** A singleton is created once and lives for the app's lifetime. Because it holds
a reference to the scoped `DbContext`, that "per-request" context never gets disposed or
recreated — it just accumulates tracked entities in its change tracker (a memory leak)
and gets used concurrently by multiple requests (`DbContext` isn't thread-safe, so this
produces intermittent, hard-to-reproduce exceptions under load).

**Fix:** Don't inject the scoped service directly. Inject `IServiceScopeFactory` and
create a new scope per unit of work:
```csharp
public class CacheWarmer : ICacheWarmer
{
    private readonly IServiceScopeFactory _scopeFactory;
    public CacheWarmer(IServiceScopeFactory scopeFactory) => _scopeFactory = scopeFactory;

    public void Refresh()
    {
        using var scope = _scopeFactory.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        // use db, then it's disposed when `scope` goes out of scope
    }
}
```
**Concept to generalize:** Know the three DI lifetimes cold — `Transient` (new every
time), `Scoped` (one per request/scope), `Singleton` (one for the app) — and specifically
the rule: a longer-lived service should never directly hold a shorter-lived one.

## 6. Closures capturing the "wrong" variable

**Trap:**
```csharp
var actions = new List<Action>();

for (int i = 0; i < 3; i++)
{
    actions.Add(() => Console.WriteLine(i));
}

foreach (var action in actions) action();   // what prints?
```
**What actually happens (C# 5.0+, which covers essentially every version in use today):**
`0`, `1`, `2` — the "expected" output. **But** if you change the loop variable declaration
style, or write the equivalent code manually with a single shared variable outside the
loop, you get `3, 3, 3` instead:
```csharp
int j = 0;
var actionsBad = new List<Action>();
while (j < 3)
{
    actionsBad.Add(() => Console.WriteLine(j));
    j++;
}
foreach (var a in actionsBad) a();   // prints 3, 3, 3
```
**Why:** A lambda doesn't capture a variable's *value* — it captures the variable itself
(technically, the compiler hoists it into a compiler-generated class field). Since C# 5,
the compiler gives each `for` loop iteration its own fresh copy of the loop variable, so
each closure captures a distinct `i`. But if a variable is declared *outside* the loop
(as with `j` above), every closure captures the exact same field, and by the time the
delegates run, that field holds its final value.

**Fix (when you deliberately need one variable per iteration but the loop won't give you
one automatically):**
```csharp
while (j < 3)
{
    int local = j;                    // fresh variable each iteration
    actionsBad.Add(() => Console.WriteLine(local));
    j++;
}
```
**Concept to generalize:** Understand that C# closures capture *variables by reference*,
not values, and know exactly which scoping construct (`for` vs `while`/manual loops)
gives you a fresh variable per iteration versus a single shared one. This shows up
constantly in event-handler registration loops and `Task.Run` inside loops.

## 7. Value types inside a class still live on the heap

**Trap:**
```csharp
public class Order
{
    public int OrderId = 0;         // a value type field...
    public Customer Customer = new Customer();  // ...next to a reference type field
}
```
**Interviewer asks:** "Where does `OrderId` get stored — stack or heap?"

**What most people say (and get wrong):** "`OrderId` is a value type, so it's on the
stack; `Customer` is a reference type, so it's on the heap."

**Why that's wrong:** Storage location is determined by the *container*, not the type
itself. Once you `new Order()`, the whole object — including every value-type field
inside it — is allocated on the heap as one contiguous block. `OrderId` only lives on
the stack if it's a local variable or parameter in its own right, completely outside any
reference-type object.

**Correct answer:** Both `OrderId` and the `Customer` reference (the reference *itself*,
i.e. the pointer/address) live inside the `Order` object on the heap. The `Customer`
*object* that reference points to is a separate heap allocation.

**Concept to generalize:** "Value types go on the stack, reference types go on the heap"
is a simplification that breaks down as soon as a value type is a field of a class, an
array element, or a captured closure variable — in all of those cases it's stored
wherever its container is stored. The only thing truly guaranteed stack-resident is a
local value-type variable in a method that isn't captured by a closure or `async` state
machine.

## 8. Mutating a struct through a property or foreach does nothing

**Trap:**
```csharp
public struct Point
{
    public int X, Y;
    public void MoveRight() => X++;
}

public class Container
{
    public Point Location { get; set; } = new Point();
}

var c = new Container();
c.Location.MoveRight();     // does this compile? what does it do?
Console.WriteLine(c.Location.X);
```
**What actually happens:** This is actually a **compile error** — "Cannot modify the
return value of 'Container.Location' because it is not a variable" — and that's the
*good* outcome, because the compiler is protecting you from a silent bug. The property
getter returns a **copy** of the struct, so calling a mutating method on it would modify
a throwaway copy that's immediately discarded.

The same trap appears in a form that *does* compile and silently fails:
```csharp
foreach (var point in points)   // points: List<Point>
{
    point.MoveRight();          // compiles if `point` isn't `readonly`... but modifies a COPY
}
// original list is unchanged
```
(In modern C#, `foreach` iteration variables are implicitly read-only, so this specific
snippet is also a compile error — but the same silent-copy problem appears the moment you
pass a struct by value into a method, or read it out of a property/array indexer and try
to mutate that local copy.)

**Why:** Structs have *value semantics* — every time one is assigned, passed as a
parameter, or returned from a property/method, you get a **copy**, not a reference to the
original. Mutating methods on a struct only affect the copy you're holding at that
moment.

**Fix:** Either make the struct immutable (preferred — create a new `Point` instead of
mutating in place) or work with it through a field/local variable you actually own:
```csharp
var p = c.Location;
p.MoveRight();
c.Location = p;      // explicitly write the modified copy back
```
**Concept to generalize:** This is the single biggest reason the .NET guidelines say
"prefer immutable structs." Mutable structs violate the mental model most developers have
(reference-type-like mutation) and produce bugs that are easy to miss because the code
often *looks* correct.

## 9. `==` vs `.Equals()` vs `ReferenceEquals()`

**Trap:**
```csharp
string a = "hello";
string b = "hel" + "lo";          // compile-time constant folding
string c = new string("hello".ToCharArray());

Console.WriteLine(a == b);                    // ?
Console.WriteLine(a == c);                    // ?
Console.WriteLine(ReferenceEquals(a, b));     // ?
Console.WriteLine(ReferenceEquals(a, c));     // ?

object o1 = new Customer { Name = "Sam" };
object o2 = new Customer { Name = "Sam" };
Console.WriteLine(o1 == o2);                  // ?
Console.WriteLine(o1.Equals(o2));             // ?
```
**What actually happens:**
- `a == b` → `true`. `b` is a compile-time constant (`"hel" + "lo"` gets folded by the
  compiler), so it's *interned* to the same string in the intern pool as `a`.
- `a == c` → `true`, but `ReferenceEquals(a, c)` → `false`. `string` overloads `==` to
  compare *content*, not reference — even though `string` is a reference type — while
  `new string(...)` deliberately creates a non-interned instance.
- `o1 == o2` → `false`. Plain `class` types (with no operator overload) use the default
  `==`, which is reference equality — and these are two distinct `Customer` objects.
- `o1.Equals(o2)` → also `false` by default, unless `Customer` overrides `Equals` (or is
  a `record`, which auto-generates value-based equality).

**Why:** `==` is *not* a fixed operator in C# — it's resolved based on the compile-time
type and can be operator-overloaded. `string` overloads it for value comparison as a
deliberate ergonomic choice. Ordinary reference types don't, so you get identity
comparison unless the class opts into value equality by overriding `Equals`/`==` — or by
being declared as a `record`, which does this automatically.

**Fix / correct usage:** For value comparison of custom types, override `Equals`/
`GetHashCode` (or use `record`). For guaranteed identity comparison regardless of any
operator overload, use `ReferenceEquals`.

**Concept to generalize:** Always know, for the type in front of you, whether `==` means
"same object" or "same value" — and that this is a *per-type* decision, not a language
constant.

## 10. Boxing turns value-type equality into reference comparison

**Trap:**
```csharp
int x = 5;
int y = 5;
object boxedX = x;
object boxedY = y;

Console.WriteLine(x == y);                 // ?
Console.WriteLine(boxedX == boxedY);       // ?
Console.WriteLine(boxedX.Equals(boxedY));  // ?
```
**What actually happens:** `x == y` → `true` (value comparison on `int`). `boxedX == boxedY`
→ **`false`** — surprising to most people. `boxedX.Equals(boxedY)` → `true`.

**Why:** Boxing wraps the `int` value in a new object on the heap. Once both sides of `==`
are statically typed as `object`, the compiler resolves `==` to `object.ReferenceEquals`
(reference comparison) because `object` has no value-equality operator overload — even
though the *contents* being boxed are equal. `.Equals()`, however, is *virtual* and `int`
overrides it to do value comparison, so it still dispatches correctly at runtime
regardless of the boxing.

**Fix:** Prefer `.Equals()` (or generics, which avoid boxing entirely) when you're not
sure both operands are statically typed as the concrete value type.

**Concept to generalize:** Boxing/unboxing isn't just a performance concern (heap
allocation + GC pressure) — it silently changes equality semantics because it moves you
from the value type's `==` to `object`'s reference-based `==`. Also worth mentioning:
this is one reason generic collections (`List<int>` vs the old non-generic `ArrayList`)
matter — generics avoid boxing altogether.

## 11. `throw ex;` destroys the original stack trace

**Trap:**
```csharp
try
{
    DoSomethingThatThrows();
}
catch (Exception ex)
{
    LogError(ex);
    throw ex;          // looks like "rethrow" — what's wrong?
}
```
**What actually happens:** The exception still propagates, but when you look at it in
your logs/debugger, the stack trace now starts at this `catch` block — the original
location deep inside `DoSomethingThatThrows()` is gone.

**Why:** `throw ex;` is treated by the runtime as throwing a *new* throw statement with
that exception object — it resets the `StackTrace` property to start from the current
point. `throw;` (no expression), by contrast, is a special "rethrow" form that preserves
the exception's original stack trace, because it doesn't create a new throw point; it
just continues propagating the existing exception object as-is.

**Fix:**
```csharp
catch (Exception ex)
{
    LogError(ex);
    throw;              // preserves the original stack trace
}
```
If you need to add context, wrap it instead of replacing it:
```csharp
catch (Exception ex)
{
    throw new InvalidOperationException("Failed while syncing order", ex); // inner exception preserved
}
```
**Concept to generalize:** This is almost always asked as "what's the difference between
`throw;` and `throw ex;`" — know it cold, because it's the difference between a debuggable
production incident and a useless stack trace pointing at your logging code.

## 12. A `return` inside `try` can be overridden by `finally`

**Trap:**
```csharp
static int GetValue()
{
    try
    {
        return 1;
    }
    finally
    {
        // nothing suspicious here... or is there?
    }
}

static int GetValueTrap()
{
    try
    {
        return 1;
    }
    finally
    {
        return 2;          // what does GetValueTrap() return?
    }
}
```
**What actually happens:** `GetValue()` returns `1` as expected. `GetValueTrap()` returns
`2` — the `finally` block's `return` **silently overrides** the `try` block's `return`,
and the compiler doesn't even warn you (though most linters/analyzers do flag it).

**Why:** `finally` is guaranteed to run no matter how the `try` exits — normal
completion, `return`, `break`, `continue`, or an exception in flight. If the `finally`
block itself contains a `return` (or a `throw`, or another jump), it takes over: it can
literally swallow an in-flight exception or replace the value the `try` was about to
return, because control hasn't actually left the method yet when `finally` runs.

**Fix:** Never put `return`, `break`, `continue`, or `throw` inside a `finally` block —
use it only for cleanup (`Dispose`, releasing locks, logging) that must run regardless of
outcome.

**Concept to generalize:** This same mechanism is why a `finally` block can also swallow
an exception that was actively propagating out of the `try`/`catch` — if `finally` exits
via its own `return`, the original exception is discarded, not just delayed. Interviewers
use this to check whether you actually understand control flow through `try/finally`
rather than treating it as a black box.

## 13. Integer division truncates — silently

**Trap:**
```csharp
int total = 7;
int count = 2;
double average = total / count;   // what's the value?
Console.WriteLine(average);
```
**What actually happens:** Prints `3`, not `3.5`.

**Why:** The type of an expression is determined by its *operands*, not by what you
assign the result to. `total / count` is `int / int`, which C# evaluates as integer
division (truncating toward zero) *before* the result is ever converted to `double` for
the assignment. By the time it becomes a `double`, the fractional part is already gone.

**Fix:** Cast at least one operand to a floating type before the division happens:
```csharp
double average = (double)total / count;   // now double / int → double division
```
**Concept to generalize:** Operator behavior in C# is resolved by the compile-time types
of the operands involved, not by the target/destination type. This same principle
explains a related trap: `decimal` and `double` don't implicitly convert to each other,
so mixing them in one expression is a compile error, not silent precision loss — which is
actually the *safe* version of this trap.

## 14. `double` isn't exact — a classic financial-code bug

**Trap:**
```csharp
double price = 0.1 + 0.2;
Console.WriteLine(price == 0.3);    // ?
Console.WriteLine(price);            // ?
```
**What actually happens:** `price == 0.3` prints `false`, and `price` itself prints
`0.30000000000000004` (or similar, depending on formatting).

**Why:** `double` is a binary floating-point type (IEEE 754). Many decimal fractions —
including `0.1` and `0.2` — can't be represented exactly in binary, the same way `1/3`
can't be represented exactly in base-10. The tiny representation error compounds across
arithmetic, so direct equality comparisons are unreliable.

**Fix:** For money or any value needing exact decimal precision, use `decimal` instead of
`double`/`float` — `decimal` is a base-10 floating type designed exactly for this:
```csharp
decimal price = 0.1m + 0.2m;
Console.WriteLine(price == 0.3m);   // true
```
When you must compare `double`s, compare within a tolerance instead of `==`:
```csharp
Math.Abs(a - b) < 0.0001
```
**Concept to generalize:** Know *when* to reach for `decimal` (money, anything requiring
exact base-10 arithmetic) versus `double`/`float` (scientific/graphics computation where
speed matters more than exact decimal representation, and small errors are tolerable).
This is one of the most commonly asked "why did this financial calculation break in
production" questions.

## 15. Shared mutable static state across requests

**Trap:**
```csharp
public class ReportController : ControllerBase
{
    private static List<string> _recentQueries = new();   // looks harmless

    [HttpGet]
    public IActionResult Get(string query)
    {
        _recentQueries.Add(query);          // "just caching the last few queries"
        return Ok(_recentQueries.TakeLast(5));
    }
}
```
**What actually happens:** Under load, this either throws
(`InvalidOperationException: Collection was modified`) or silently produces wrong/mixed
results across unrelated users' requests, and the list grows forever (memory leak).

**Why:** `static` fields belong to the *type*, not to any instance — and ASP.NET Core
creates a new controller instance per request but only one static field for the whole
application's lifetime, shared by every concurrent request on every thread in the
pool. `List<T>` is not thread-safe, so concurrent `Add()` calls from different requests
race with each other.

**Fix:** Don't use mutable `static` state for anything per-request. If you genuinely need
process-wide shared state, use a thread-safe collection (`ConcurrentBag<T>`,
`ConcurrentQueue<T>`) with a bounded size, or better, push it into a proper cache
(`IMemoryCache`, distributed cache) that's designed for concurrent access and eviction.

**Concept to generalize:** This connects directly to trap #5 (captive dependency) —
both are really the same underlying mistake: giving something a *longer lifetime and
wider sharing scope* than it should have. Whenever you see `static` mutable state in a
web app, ask "what happens when two requests hit this at the same instant?"

## 16. Calling a virtual method from a constructor

**Trap:**
```csharp
public class Base
{
    public Base()
    {
        Initialize();          // calls a virtual method during construction
    }

    public virtual void Initialize() => Console.WriteLine("Base.Initialize");
}

public class Derived : Base
{
    private readonly string _name = "derived-name";

    public override void Initialize()
        => Console.WriteLine($"Derived.Initialize, name = {_name}");
}

var d = new Derived();   // what prints?
```
**What actually happens:** Prints `Derived.Initialize, name = ` (empty/null) — **not**
`"derived-name"` — even though `_name` has a field initializer.

**Why:** Constructors run base-class-first. `Base`'s constructor calls `Initialize()`,
which is virtual, so the runtime correctly dispatches to `Derived.Initialize` (that part
works as expected via normal polymorphism). But `Derived`'s own field initializers
(`_name = "derived-name"`) haven't run yet — they execute *after* the base constructor
returns, as part of `Derived`'s own constructor body. So the override runs against a
half-constructed object where its own fields still hold their default values.

**Fix:** Don't call virtual/overridable members from a constructor. If subclasses need to
customize initialization, use a separate, explicitly-called `Init()` method, a factory
method, or constructor parameters instead of relying on override dispatch during
construction.

**Concept to generalize:** This is a real, well-documented C# gotcha (also flagged by
static analyzers as CA2214) that trips people up because polymorphism *does* work
correctly here — the surprise isn't about virtual dispatch, it's about **initialization
order**: base constructor → base field initializers already done → base constructor body
runs (including any virtual calls) → *then* derived field initializers → derived
constructor body.

## 17. Extension methods silently lose to instance methods

**Trap:**
```csharp
public static class StringExtensions
{
    public static bool IsValid(this string s) => !string.IsNullOrWhiteSpace(s);
}

// ... six months later, someone adds a new instance method to a class:
public class Order
{
    public string Reference = "";
    public bool IsValid() => Reference.Length == 10;   // completely different logic!
}

// existing calling code, unchanged:
Order o = new Order();
bool result = o.IsValid();   // did this call the extension or the instance method?
```
**What actually happens:** It silently calls `Order.IsValid()` (the new instance
method) — even though this code compiled and worked fine before that method existed, and
even though the extension method still exists and is still `using`-imported. No compiler
warning, no error — just a behavior change.

**Why:** C# method resolution always prefers an applicable **instance method** over an
**extension method** if both exist for a given call — extension methods are only
considered when no matching instance member is found. This is by design (to let a real
member always "win" over a syntactic sugar call), but it means adding a member to a class
can silently change the meaning of every extension-method call site that happens to match
its name and signature, with zero compiler feedback.

**Fix:** There's no purely mechanical fix — this is a design-awareness issue. Practical
mitigations: give extension methods distinctive names unlikely to collide
(`IsValidReference()` rather than `IsValid()`), keep good test coverage on behavior (not
just compilation) so a silent redirection gets caught, and be deliberate when adding
instance methods to types that already have extension methods floating around the
codebase.

**Concept to generalize:** Extension methods are compile-time syntactic sugar for static
method calls, resolved by overload resolution rules that always favor "real" members.
Interviewers ask this to see if you understand extension methods aren't part of the type
itself — they're just found by the compiler when nothing better matches.

## 18. `default(enum)` doesn't have to be a valid member

**Trap:**
```csharp
public enum OrderStatus
{
    Pending = 1,
    Shipped = 2,
    Delivered = 3
}

OrderStatus status = default;   // what's the value?
Console.WriteLine(status);
Console.WriteLine((int)status);
Console.WriteLine(Enum.IsDefined(typeof(OrderStatus), status));
```
**What actually happens:** Prints `0`, `0`, and `False` — `status` is neither `Pending`,
`Shipped`, nor `Delivered`. `Console.WriteLine(status)` prints the literal number `0`
because there's no matching name.

**Why:** Enums are backed by an integral type (`int` by default) and, like all value
types, `default` gives you the all-zero bit pattern — regardless of whether `0` was
assigned to any member. Because nobody declared a member equal to `0` here, the "default"
state of this enum is technically invalid/undefined from the domain's point of view.

**Fix:** Deliberately give every enum a `0`-valued member representing a sensible
default/unset state (a common convention: name it `None` or `Unknown`):
```csharp
public enum OrderStatus
{
    None = 0,        // now default(OrderStatus) is meaningful
    Pending = 1,
    Shipped = 2,
    Delivered = 3
}
```
And validate untrusted input against `Enum.IsDefined` (or a pattern-matching exhaustive
`switch`) rather than assuming a variable of enum type always holds one of the "named"
values — casting *any* integer to an enum type compiles and runs without error, valid
member or not.

**Concept to generalize:** Enums in C# are not a closed set the way they might be in some
other languages — they're thin wrappers over integers, so both `default` and explicit
casts can produce values with no corresponding name. Always design the `0` case on
purpose.

## 19. `yield return` defers side effects, including exceptions

**Trap:**
```csharp
IEnumerable<int> Divide(int[] numbers, int divisor)
{
    Console.WriteLine("Starting division");   // when does this actually print?
    foreach (var n in numbers)
        yield return n / divisor;             // what if divisor is 0?
}

var result = Divide(new[] { 10, 20 }, 0);
Console.WriteLine("Method called, no exception yet");
foreach (var r in result)                      // exception actually throws HERE
    Console.WriteLine(r);
```
**What actually happens:** `"Method called, no exception yet"` prints *before*
`"Starting division"` does, and the `DivideByZeroException` is thrown only when the
`foreach` loop starts pulling values — not at the moment `Divide(...)` was called.

**Why:** A method containing `yield return` doesn't execute any of its body when called —
the compiler transforms it into a state machine (implementing `IEnumerable<int>`) whose
code only runs incrementally, one step at a time, each time `MoveNext()` is called by an
enumerator (which `foreach` does under the hood). Calling `Divide(...)` just constructs
that state machine object; none of your code inside it has run yet.

**Fix:** This is usually a "know it, don't fight it" situation — but if you need
*validation* to happen eagerly (immediately, not deferred), split the method: validate
in a normal (non-iterator) wrapper method, and put the `yield return` logic in a private
iterator method it calls:
```csharp
IEnumerable<int> Divide(int[] numbers, int divisor)
{
    if (divisor == 0) throw new ArgumentException("divisor cannot be 0"); // runs immediately
    return DivideCore(numbers, divisor);
}

IEnumerable<int> DivideCore(int[] numbers, int divisor)
{
    foreach (var n in numbers)
        yield return n / divisor;
}
```
**Concept to generalize:** This is the same deferred-execution family as traps #3 and
#4 — `yield return`, LINQ's `Where`/`Select`, and `async` methods all use compiler-
generated state machines that separate *"code that builds the pipeline"* from *"code
that actually runs,"* and interviewers use exactly this kind of "when does this line
actually execute" question to test whether you understand the state-machine
transformation, not just the syntax.

## 20. `record` equality vs `class` equality

**Trap:**
```csharp
public class CustomerClass
{
    public string Name { get; init; } = "";
}

public record CustomerRecord(string Name);

var c1 = new CustomerClass { Name = "Sam" };
var c2 = new CustomerClass { Name = "Sam" };
Console.WriteLine(c1 == c2);            // ?
Console.WriteLine(c1.Equals(c2));       // ?

var r1 = new CustomerRecord("Sam");
var r2 = new CustomerRecord("Sam");
Console.WriteLine(r1 == r2);            // ?
Console.WriteLine(r1.Equals(r2));       // ?
Console.WriteLine(ReferenceEquals(r1, r2)); // ?
```
**What actually happens:** Both `c1 == c2` and `c1.Equals(c2)` are `false` (two distinct
objects). Both `r1 == r2` and `r1.Equals(r2)` are `true` — but `ReferenceEquals(r1, r2)`
is still `false`.

**Why:** `record` is still a *reference type* (unless declared `record struct`) — it's
allocated on the heap and assigning it copies the reference, just like a class. The
difference is that the compiler auto-generates value-based `Equals`, `GetHashCode`, and
`==`/`!=` operator overloads for records, comparing every declared property, whereas an
ordinary `class` falls back to `object`'s default reference-based equality unless you
explicitly override it.

**Fix/usage guidance:** Reach for `record` specifically when you want a type whose
identity *is* its data (DTOs, value objects, message/event payloads, anything you'll
compare or use as a dictionary key by content). Keep using `class` for entities with a
genuine identity independent of their current property values (e.g., a `Customer` row
that keeps the "same identity" even after its `Name` changes) — for those, reference
equality (or an explicit `Id`-based `Equals` override) is usually what you actually want.

**Concept to generalize:** "Record vs class" screening questions are really testing
whether you understand *why* the two exist side by side rather than one replacing the
other — it's an equality-semantics decision, not a syntax preference.

## How to use this list

Don't just memorize the "what prints" answers — for each one, be ready to explain the
*mechanism* underneath (deferred execution / state machines, lifetime and scope
mismatches, value vs reference semantics, compile-time vs runtime resolution). That's
what separates "I've seen this trick before" from "I actually understand C#," and it's
exactly what interviewers are listening for when they ask a follow-up like *"why does
that happen?"* after you get the initial answer right.
